## 二、🔴 严重风险（Critical）

### C1. 内置模型 API Key 可被任意登录用户覆盖 —— 越权写漏洞

- **位置**：`app/api/models/[modelId]/route.ts:28-34`（PUT 分支）
- **风险类型**：权限校验缺失 / 越权写
- **严重程度**：🔴 严重
- **问题描述**：内置模型（`owner_id` 为空，即平台级配置的 Kimi/智谱/DeepSeek 等模型）更新时只校验 `body.api_key` 存在，**未校验操作者是否为管理员**。任何登录用户都能通过 `PUT /api/models/{id}` 覆盖平台级模型 API Key。
- **攻击影响**：
  1. 攻击者把自己的 API Key 写入内置模型 → 全平台所有用户的解析/检索请求都转发到攻击者账号 → 攻击者可观察全部用户的专利文档与检索 Prompt（**数据泄露**）；
  2. 或写入无效 Key → 平台检索功能整体瘫痪（**DoS**）。
- **修复建议**：
  ```ts
  // models/[modelId]/route.ts:28 前置管理员校验（复用 requireAdmin 的鉴权逻辑或新增 requireAdminOnly）
  if (!existing.owner_id) {
    await requireAdmin() // 仅管理员可改内置模型
    ...
  }
  ```

### C2. 模型 API Key 明文存储 —— 敏感数据泄露

- **位置**：`app/api/models/route.ts:57`、`app/api/models/[modelId]/route.ts:30,51`
- **风险类型**：敏感数据存储 / 加密缺失
- **严重程度**：🔴 严重
- **问题描述**：字段名为 `api_key_encrypted`（暗示应加密），但代码直接将用户提交的 `api_key` 明文写入数据库。数据库一旦泄露（备份外流、SQL 注入、管理后台误操作），所有平台/用户模型 Key 全部暴露。
- **修复建议**：引入加密层（如 `@nestjs/encryption`、AWS KMS、或应用层 AES-256-GCM），写入前加密、读取后解密；或在数据库层用 `pgcrypto`。至少应：加密存储 + 解密仅在 worker 调用时进行 + 管理界面永远不回显明文。

### C3. service_role Key 在非 Admin 路由中广泛使用 —— 架构级越权隐患

- **位置**：`app/api/preferences/route.ts:29`、`app/api/queue-status/route.ts:12`、`app/api/documents/route.ts:18`、`app/api/documents/[documentId]/route.ts:52`、`app/api/jobs/route.ts:34,83`、`app/api/jobs/retry/route.ts:32`、`app/api/jobs/[jobId]/retry-tasks/route.ts:33`、`app/api/models/route.ts:49`、`app/api/strategies/route.ts:41` 等 12+ 处
- **风险类型**：权限校验 / 最小权限原则违反
- **严重程度**：🔴 严重（架构性）
- **问题描述**：`createServiceClient()`（service_role key）完全绕过 RLS，所有数据隔离依赖各路由代码里手动 `.eq('user_id', user.id)`。**任何一处遗漏或未来新增路由忘记加条件，即产生 IDOR 越权**。当前已发现两处薄弱点：
  - `app/api/documents/[documentId]/route.ts:52-58`（PATCH）：先查询归属校验，随后用 service client 更新时**只 `.eq('id', documentId)` 未再次带 `user_id` 条件**（TOCTOU 窗口 + 缺第二道防线）；
  - `app/api/documents/route.ts:18-27`（POST）：`fileUrl`/`fileName`/`fileType` 未做任何校验直接入库。
- **修复建议**：
  1. 优先为 `patent_documents`、`search_jobs`、`reports`、`profiles` 等表配置**正确的 RLS 策略**，让普通路由走 anon/authenticated 客户端，service client 仅限 worker 与 admin；
  2. 所有 service client 更新/删除操作必须同时携带 `.eq('user_id', user.id)` 作为第二道防线；
  3. 建立代码规范：新增路由禁止直接 import `createServiceClient`，必须经统一的数据访问层。

### C4. 报告 HTML 存储型 XSS —— 未转义字段注入

- **位置**：`worker/src/services/report.ts:363`（`errorMsg` 未转义）、`report.ts:361,364`（`platform`/`strategy` 未转义）、渲染端 `components/report/report-preview.tsx:22`（`sandbox="allow-same-origin allow-popups allow-popups-to-escape-sandbox"`）
- **风险类型**：XSS / 输入输出编码
- **严重程度**：🔴 严重
- **问题描述**：`buildHtmlReport` 中大部分字段（title/authors/relevance_desc/warnings）都做了 `escapeHtml`，但 **`pathSummary` 的 `errorMsg`、`platform`、`strategy` 直接拼接进 HTML**。`errorMsg` 来自 AI 调用/数据库的错误消息，若 AI 返回内容或模型配置被恶意构造，可注入任意 HTML/脚本。报告以 `iframe srcDoc` 渲染且 `sandbox` 含 `allow-same-origin`——同源 iframe 内注入一旦配合未来改动（如增加 `allow-scripts`）或利用非脚本向量，即可窃取主页面会话；管理员报告页（`app/(app)/admin/reports/[jobId]/page.tsx`）也渲染同一 HTML，攻击链可升级为管理员会话劫持。
- **修复建议**：
  1. `errorMsg`、`platform`、`strategy` 全部套 `escapeHtml()`；
  2. `report-preview.tsx` 的 sandbox **移除 `allow-same-origin`**（报告是纯展示内容，不需要同源），仅保留 `allow-popups`；
  3. 服务端再兜一层：报告写入时对 `errorMsg` 做 HTML 实体编码。

## 三、🟠 高风险（High）

### H1. 任务重排入队失败 → "queued 僵尸任务"（状态不一致）

- **位置**：`worker/src/services/job-retry.ts:44-58, 72-77`
- **风险类型**：状态机不一致 / 错误处理缺陷
- **严重程度**：🟠 高
- **问题描述**：`handleJobFailure` 先执行 `UPDATE ... SET status='queued', retry_count+1`（成功），随后调用 `send_pgboss_job` RPC 入队。若 RPC 失败或乐观锁未命中，走 `markJobFailed`——但 `markJobFailed` 的条件是 `.eq('status', 'running')`，此时记录状态已是 `queued`，**条件不命中，更新无效** → 任务永远卡在 `queued` 且队列中不存在对应 job，看门狗也救不回来（只扫 `running`）。
- **修复建议**：`markJobFailed` 增加状态条件分支：`status IN ('running','queued')`；或在 RPC 失败前先回滚 `status='failed'` 再通知。

### H2. 硬超时后 execution 继续执行 → 双写竞争（任务重复执行）

- **位置**：`worker/src/handlers/search-job.ts:160-162`
- **风险类型**：并发竞态
- **严重程度**：🟠 高
- **问题描述**：`Promise.race([execution, hardTimeout])` 超时 reject 后，**execution 并未被取消**（JS 无法强杀 in-flight promise），其内部 `updateJob('completed')`、`generateReport` 等仍会继续执行并写库。与此同时 `catch` 分支调用 `handleJobFailure`（重排为 queued 或判 failed）。两条写路径竞争同一 `search_jobs` 记录 → 最终状态取决于时序：可能 `completed` 被 `failed` 覆盖，或重排后的新执行与旧 execution 并发跑同一 jobId → **子任务重复执行、报告重复生成**。
- **修复建议**：
  1. 超时后设置 `aborted` 标志，execution 内每个 await 后检查并提前 return（协作式取消）；
  2. 所有终态写入（completed/failed）使用**原子状态迁移**：`.eq('status', 'running')` 条件更新，只允许 running→completed / running→failed 单向迁移，失败则说明状态已被他人改动；
  3. 生成报告前校验 job 仍为 running。

### H3. 看门狗与在跑任务竞争（30min 阈值 vs 25min 硬超时）

- **位置**：`worker/src/index.ts:106-118` + `worker/src/services/job-retry.ts:102-125`（markJobFailed）
- **风险类型**：并发竞态
- **严重程度**：🟠 高
- **问题描述**：看门狗每 60s 把 `running` 超过 30min 的任务直接判 `failed`。但 handler 硬超时 25min，AI 调用（Kimi 等）耗时可达 5-8min，若任务在 25~30min 窗口内完成，会先被看门狗标 `failed`，随后 execution 又写 `completed` → 用户看到"失败"但实际成功（或反之），且 `markJobFailed` 的通知与最终状态矛盾。多 worker 实例部署时竞争更激烈。
- **修复建议**：看门狗阈值应显著大于硬超时（如 40min）；`markJobFailed` 与 execution 的终态写入都改用原子状态迁移（见 H2.2）；看门狗判失败后附加"最终以 worker 结算状态为准"的合并逻辑。

### H4. 元数据富化 SSRF —— 重定向绕过 + IP 表示法绕过

- **位置**：`worker/src/services/enrichment.ts:198-207`（`fetchPageMeta`）、`enrichment.ts:336-348`（`isPrivateUrl`）
- **风险类型**：SSRF / 输入验证
- **严重程度**：🟠 高
- **问题描述**：
  1. `isPrivateUrl` 仅按 hostname 字符串匹配内网段，**整数/十六进制 IP 表示**（如 `2130706433`、`0x7f000001`、`0177.0.0.1`）可绕过正则，Node fetch 解析后实际访问内网；
  2. `fetchPageMeta` 使用 `redirect: 'follow'`，**初始 URL 合法但可 302 重定向到内网地址**（如 `http://169.254.169.254/latest/meta-data/` 云凭据端点）。
  3. URL 来源是 AI 生成的搜索结果 → 恶意文档内容可诱导 AI 输出恶意 URL 作为攻击向量。
- **修复建议**：
  1. 用 DNS 解析后校验 IP（`dns.lookup` 后比对私有段），而非字符串匹配；
  2. `redirect: 'manual'` 并逐跳校验；
  3. 增加目标 URL 白名单或禁止非 http(s)。

### H5. 用户自定义模型 `api_base_url` 未校验协议/主机 —— SSRF 向量

- **位置**：`app/api/models/route.ts:45-46, 55`、`worker/src/adapters/openai-compat.ts:48`
- **风险类型**：SSRF / 输入验证
- **严重程度**：🟠 高
- **问题描述**：`api_base_url` 仅校验非空，未校验 `http(s)` 协议。worker 会 `fetch(${baseUrl}/chat/completions)`——恶意用户可配置 `http://169.254.169.254` 或内网地址，worker 即成为内网访问代理；配置 `http://内网:5432` 等还可探测端口。
- **修复建议**：校验 `api_base_url` 必须以 `https://` 开头（或至少 http/https 且主机名非私有地址），存储时规范化。

### H6. 重新解析（reparse）入队失败 → 文档永久 pending

- **位置**：`app/api/documents/[documentId]/reparse/route.ts:39-52`
- **风险类型**：状态不一致 / 错误处理缺陷
- **严重程度**：🟠 高
- **问题描述**：先 `UPDATE parse_status='pending'`，随后 `sendBossJob` **无 try-catch**。入队失败 → 抛异常被 withApiHandler 捕获返回 500，但文档已置 `pending`，队列中无任务 → 文档永远停留在 pending，用户无法再发起检索。
- **修复建议**：参照 `app/api/jobs/route.ts:43-53` 的写法：try-catch 包裹 `sendBossJob`，失败时回滚 `parse_status` 为原值（读取时先记录）。

### H7. 文件上传/解析无大小限制 —— 资源耗尽 DoS

- **位置**：上传端 `app/(app)/search/new/step-1/page.tsx:124`（`supabase.storage.upload` 无大小/类型限制）；下载端 `worker/src/services/supabase.ts:11-21`（`downloadFile` 全量读入内存 Buffer）；解析端 `worker/src/parsers/xlsx.ts:8`（`xlsx.read` 无 zip-bomb 防护）
- **风险类型**：资源泄漏 / DoS
- **严重程度**：🟠 高
- **问题描述**：任意登录用户可上传超大文件或 zip-bomb 类 xlsx。worker 将整个文件载入内存并解析，超大 PDF/xlsx 解压后可迅速耗尽 worker 内存（pm2 `max_memory_restart: 600M` 触发反复重启 → 队列停摆）。
- **修复建议**：上传接口校验 `file.size`（建议 ≤ 50MB）与 MIME；`downloadFile` 增加超时与大小守卫；`xlsx.read` 前校验解压后大小或使用 `sheet_to_json` 流式读取。

### H8. parse-job 缺少硬超时

- **位置**：`worker/src/handlers/parse-job.ts:40-45`
- **风险类型**：资源泄漏 / 健壮性
- **严重程度**：🟠 高
- **问题描述**：`callWithRetry`（3 次重试 × 300s 超时 + 退避）总时长可达 15 分钟以上且**无外层硬超时**（search-job 有 `HARD_TIMEOUT_MS`，parse-job 没有）。若文件解析（超大 PDF）或 AI 调用挂起，handler 永不返回，pg-boss 30min 过期后 job 会被重复投递，且本地 Concurrency=1 会阻塞整个 parse 队列。
- **修复建议**：为 `handleParseJob` 增加与 search-job 同等的硬超时 guard（如 20min），`parseFile` 也套 `withTimeout`。
